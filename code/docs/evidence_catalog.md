## Identifier and timestamp interpretation

- JSON bundles use exported_at, snapshots[].captured_at and nested records. Common joins are resource_id, customer_reference/user_id, direct fields, and system-specific order, ticket, backup, export, connector, audit or search IDs. Records may have created/updated/observed times. Operational history is a sequence of claims, not necessarily final state.
- Eleven service-resource exports are evidence_62, 65, 68, 71, 74, 77, 80, 83, 86, 89 and 92, dated Jan 29-Sep 15 2026. They use exported_at and per-resource observed_at; system sections vary. The manifest table is authoritative.
- Inventory SQL uses snapshot_scope(origin_system,captured_at), relational resource_id/customer_reference/direct-identifier columns and updated_at. Other snapshots compare primary with read, regional, reporting or failover tables. record_json carries identifiers and state; compare the same resource across sides.
- Logs are timestamped UTF-8 streams. Extract timestamp, event, service/system, resource_id, subject/match key, result/status and trace/correlation ID. Families include direct resource readbacks, application/service traces, search diagnostics, delivery, syslog, cloud runtime and operations. Log claims still need evidence-scope interpretation.
- PDFs contain selectable text and were extracted page-by-page. PNGs were visually inspected; screenshots may show selected and unrelated rows together.
- Sep 30/Oct 1 evidence and later internal record times fall after some audit_at values. Apply each case cutoff to manifest capture and internal times.
